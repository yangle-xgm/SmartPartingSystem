## 一、结论摘要

1. **核心链路功能完整**：登录/注册、双端路由守卫、五个业主 Tab、四类订单分组、车辆绑定与解绑、访客核验码、通知已读、管理端 14 个页面全部按预期渲染与交互，未发现阻断级（P0/P1）缺陷。
2. **发现 1 个真实缺陷（P2）**：后端 5xx 时，H5 与管理端都会把英文框架原文 `Internal Server Error` 直接弹给用户，而不是「服务繁忙，请稍后再试」。两端同源（`safeMessage` 的敏感词黑名单只覆盖 SQL/Java 堆栈，未覆盖英文 HTTP 短语），已用 `test.fail` 固化复现。
3. **2 条数据/体验观察项（P3）**：历史通知文案 `停放在` 后面缺车位号（修复前产生的历史数据）；H5 车辆页悬浮「绑定车辆」按钮会压住列表卡片的「解绑」按钮。
4. **健壮性表现良好**：500、网络中断、业务 401、空列表、空小区档案、重复编号、负数价格、超长输入、99+ 未读、320px 窄屏等 11 类边界场景均按预期降级，没有出现白屏或控制台报错。
5. **风险集中在未覆盖域**：真实支付回调、物业管理员（role=1）页面、iOS/Safari 与微信内置浏览器、长列表性能、无障碍、并发与弱网 —— 详见第六节。

## 五、发现的问题

### DEF-01（P2 · 中）后端 5xx 时把英文框架原文弹给用户

| 项 | 内容 |
|---|---|
| 影响端 | 业主端 H5 + 管理端 Web（同一套 `safeMessage` 逻辑，两端各有一份实现） |
| 复现 | 拦截 `GET /api/user/info`（H5）或 `GET /api/parking/**`（Web），返回 `500 {"code":500,"message":"Internal Server Error"}` |
| 预期 | 提示「服务繁忙，请稍后再试」 |
| 实际 | 提示 `Internal Server Error` |
| 严重级别 | P2（不阻断功能，但把基础设施错误以英文原文暴露给终端用户，观感与安全感较差） |
| 根因 | `utils/request.js` 的 `safeMessage(code, backendMsg)` 判定顺序是「后端 message 干净就直接用」，而「干净」仅由 `INTERNAL_MSG`（`###|SQLState|SQL\b|MyBatis|java\.|Exception|Out of range|Data truncation`）+ 长度 ≤ 80 判定。`Internal Server Error`、`Bad Gateway`、`Service Unavailable` 这类英文框架短语既不命中黑名单也不超长，于是被当成可用业务文案。 |
| 修复建议 | ① 语义上更稳的做法：`code >= 500` 一律不信任后端 message，直接走前端通用文案（5xx 的 message 天然是框架/异常原文，业务语义弱），原文只 `console.error` 留档；② 若需保留部分 5xx 业务文案，则补一个英文框架短语黑名单：`/^\s*(Internal Server Error|Bad Request|Unauthorized|Forbidden|Not Found|Service Unavailable|Gateway Time-?out|Bad Gateway)\s*$/i`；③ H5 与 Web 两处同步改（当前是复制粘贴的两份实现，建议抽到共享包避免再次分叉）。 |
| 回归固化 | `h5-resilience.h5.spec.js` 与 `pc-functional.pc.spec.js` 中各有一条 `test.fail` 用例；修复后删除 `test.fail` 即自动转为常规回归。 |

### OBS-01（P3 · 低）历史通知文案「停放在」后缺车位号

| 项 | 内容 |
|---|---|
| 影响端 | H5 通知中心、PC 通知中心 |
| 证据 | 真机截图：`您的访客车辆 京B80950 已于 2026-11-17 10:02:30 入场，停放在`（末尾空缺） |

| 建议 | ① 清理或回填 2026-11-17 11:53 之前的历史 `entry` 通知（可按 `content LIKE '%停放在'` 定位）；② 若产品不接受历史脏数据，配置一次性数据修正脚本；③ 长期可在通知模板层做「变量缺失则整句省略」的兜底，而不是拼接后留半句。 |

## 六、尚未覆盖的风险点

| # | 风险点 | 说明 | 建议优先级 |
|---|---|---|---|
| R1 | 真实支付回调 | 只验证到「支付方式抽屉」与「取消」，未执行微信/支付宝模拟支付的成功/失败/重复支付回调，也未验证支付后订单状态与通知联动 | 高 |
| R2 | 物业管理员（role=1） | 仅覆盖 role=0（业主）与 role=2（超管）。`property_mgr` 的菜单组合、车位/订单/设备/统计页的写权限未验证 | 高 |
| R3 | 跨浏览器 / 内嵌 WebView | 仅在 Edge 120 与小米浏览器（Chromium 内核）验证。Safari/iOS WebView、微信内置浏览器、鸿蒙浏览器的 `safe-area`、`position: fixed`、`-webkit-` 前缀行为未验证 | 高 |
| R4 | 并发与弱网 | 未测 3G/弱网抖动、15s 超时边界、并发 401 触发 refresh 的成功路径（只测了 refresh 失败→登出）、双击提交幂等 | 中 |
| R5 | 长列表性能 | H5 订单/通知一次性加载全量，未用数百条数据验证首屏渲染耗时、滚动流畅度与内存；Web 表格分页的末页/越界页码未测 | 中 |
| R6 | 无障碍 | 未验证键盘 Tab 顺序、焦点可见性、屏幕阅读器播报、色彩对比度（深色品牌页与金色 CTA 对比度存疑） | 中 |
| R7 | 安全类前端风险 | 未做 XSS 注入（通知标题/反馈内容是否被 `v-html` 渲染）、CSRF、token 在 localStorage 的 XSS 可读性评估 | 中 |
| R8 | 主题切换边界 | 管理端 `.light` 类挂在 `<html>`，未验证弹层 teleport 到 body 后在深色/浅色切换瞬间的样式错乱 | 低 |
| R9 | 极窄屏与横屏 | 只测 320px 到 430px 竖屏，未测 280px（折叠屏外屏）与横屏（844×390）下 TabBar 与弹层表现 | 低 |
| R10 | 时间与时区 | 列表时间直接展示后端字符串（`replace('T',' ')`），未验证跨时区、后端返回 `null`/异常格式时的兜底 | 低 |
| R11 | 浏览器前进/后退 | 未系统验证 `history` 前进后退与 `replace` 混用后的栈行为（仅覆盖了深链接兜底一例） | 低 |
| R12 | 通知/订单数据规模边界 | 「99+」用接口 mock 验证，未在真实 100+ 未读数据下验证角标与筛选性能 | 低 |

## 七、复跑方式

```bash
cd scripts/e2e
# 依赖：网关 8080 + 各微服务 + MySQL/Redis 容器在线，两端 dev server 已启动
H5_BASE_URL=http://localhost:3001 npx playwright test --project=h5-ui --project=pc-ui

# 只看本次新增的功能用例
H5_BASE_URL=http://localhost:3001 npx playwright test --project=h5-ui h5-functional h5-resilience
npx playwright test --project=pc-ui pc-functional

# 查看 HTML 报告
npx playwright show-report
```

新增/修改的测试文件：

- `scripts/e2e/tests/ui/h5-functional.h5.spec.js`（22 条：登录、守卫、导航、表单、弹窗、数据展示）
- `scripts/e2e/tests/ui/h5-resilience.h5.spec.js`（10 条：异常、空态、401、响应式、边界）
- `scripts/e2e/tests/ui/pc-functional.pc.spec.js`（21 条：登录、角色守卫、14 页渲染、弹窗表单、404、UA 跳转、异常）

用例设计约定：
- 除登录页自身外，统一通过 API 取业主 token 注入 `localStorage`，避免每条用例消耗一次图形验证码；
- 仍保留 1 条走完整 UI 登录（真实验证码 + Redis 取答案）的用例，保证登录链路本身被真实覆盖；
- 视图层断言优先用语义选择器与文案，避免绑定具体 DOM 层级；
- 会产生写操作的用例一律「只到确认弹窗并取消」，或执行后按快照还原。
