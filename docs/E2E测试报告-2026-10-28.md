## 一、总体结论

| 维度 | 结论 | 通过率 |
| --- | --- | --- |
| 接口路径/方法对齐 | 前端调用的 47 个路径在后端**全部存在**，方法一致 | 100% |
| 参数绑定方式 | 全部对齐（`@RequestParam` / `@RequestBody` 无错配） | 100% |
| 返回结构消费 | 存在 3 类系统性错配（车牌密文、错误码、区域枚举） | 78% |

**一句话结论**：功能骨架完整、主流程可闭环，但**权限收口缺失**和**敏感字段解密遗漏**是两个必须在上线前解决的结构性问题；统计口径与异常分支属于功能正确性缺陷。

## 二、P0 级问题（安全/资金，必须修）

### P0-1 内部接口对公网免鉴权，业主可直接退款

`/api/**/internal/**` 被网关整段放进白名单，而 AGENTS.md 明确规定"网关不对外暴露 `/internal/**`"。

**实测**：业主 token 调用
```
POST /api/payment/internal/refund?payNo=PAY202610281919543575
→ {"code":200,"message":"操作成功"}
```
该笔流水随即由「支付成功」变为「已退款」，支付页"已退款金额"同步增加。

同类可被业主直接执行的内部接口：
| 接口 | 后果 |
| --- | --- |
| `POST /api/payment/internal/refund` | 任意退款 |
| `POST /api/order/internal/confirm-payment` | 伪造支付成功 |
| `PUT /api/parking/internal/space/{id}/status` | 任意改车位状态 |
| `POST /api/order/internal/device-entry` | 伪造设备入场 |
| `GET /api/user/internal/owner-ids` | 拉取全部业主 ID |

**建议修复**：网关白名单移除 `/api/**/internal/**`；改为服务间以固定内网 Header（如 `X-Internal-Token`）校验，且仅允许内网来源 IP。

### P0-2 业主可群发全站通知

```
POST /api/notify/admin/send  {"target":0,"title":"越权","content":"x"}
→ code=200，全站每个用户收到一条
```
**建议**：网关把 `/api/notify/admin/**` 与服务端 `role in (1,2)` 双重校验。

### P0-3 业主可增删车位、可回复任意反馈、可读全量反馈

| 调用 | 实测结果 |
| --- | --- |
| `POST /api/parking/space`（新增 ZZ-999） | ✅ 成功创建，管理员可查到 |
| `GET /api/notify/feedback/all` | ✅ 返回全部业主反馈（含内容） |
| `POST /api/notify/feedback/{id}/reply` | ✅ 成功写入物业回复 |

**建议**：`/api/parking/space*` 写操作、`/feedback/all`、`/feedback/{id}/reply` 统一纳入 `ADMIN_ONLY_PATTERNS`。

### P0-4 订单列表车牌返回 AES 密文，前端直接渲染乱码

**现象**（浏览器实测 `/order` 页面文本）：
```
ORD202610281924191211  YciTjwKuLP86xnjX3Op45Q==  A-005  …
ORD202610281920382164  VsuQrPh5TIEmli+L567cHA==  A-004  …
```
影响页面：PC `/order`、`/my-orders`、`/dashboard`、`/notification`、设备页"访客入场结果"；H5 `/home`、`/orders`。

**根因（3 处）**：
1. `ParkingOrderServiceImpl.pageList()` 第 237 行
   ```java
   result.getRecords().forEach(ParkingOrderServiceImpl::decryptPlateNo);
   ```
   `decryptPlateNo` 返回 `String`，方法引用被当作 `Consumer`，**返回值被丢弃**，对象未被修改。
2. `createEntryOrder()` 返回前未解密 → 入场接口返回密文。
3. `VisitorInvite.plateNo` 同样为密文（该实体另有 `plateNoMasked`，前端已正确使用）。

**建议修复**：
```java
result.getRecords().forEach(o -> o.setPlateNo(decryptPlateNo(o)));
```
并在 `createEntryOrder` / `deviceEntry` 返回前统一解密；更好的做法是对外只返回 `plateNoMasked`，明文仅管理员可见。

### P0-5 支付金额与订单金额脱钩

```
订单应付 0.00 元 → POST /api/payment/create?amount=0.01 → 支付成功
→ /api/stats/dashboard 的 todayIncome 变为 0.01
```
`PaymentRecordServiceImpl.createPayment()` 只校验订单存在/未支付/未退款，**从不比对 `amount` 与订单 `amount`**。

**建议**：`amount` 以订单应付金额为准，忽略前端传值（或校验差值）；`amount<=0` 直接走"免支付"分支，不生成流水。

### P0-6 支付超时复用"已退款"状态

`PaymentTimeoutTask.processTimeout()` → `record.setPayStatus(2)`（`PAY_STATUS_REFUNDED`）。
后果：从未付款的超时单被计入"已退款金额"，退款统计虚增；前端只能显示"已退款/已关闭"这种含混文案。

**建议**：新增 `PAY_STATUS_CLOSED(3)`（或复用 `4 支付失败`），前端按 `2=已退款 / 3=已关闭严格区分；`Constants` 补齐 `PAY_STATUS_FAILED(4)` 常量，消除 `setPayStatus(4)` 魔法值。

## 三、P1 级问题（功能正确性）

### P1-1 设备联动入场对"未注册/黑名单"车牌抛事务回滚异常

**实测**：
```
POST /api/order/internal/device-entry?plateNo=沪Z99999
→ {"code":500,"message":"Transaction rolled back because it has been marked as rollback-only"}
```
前端设备页看到的是 `recognized:false, message:"MQTT联动处理超时，请检查 device 服务日志"` —— **提示与真实原因完全不符**，运维会被误导去查 MQTT。

**根因**：`deviceEntry()` 中
```java
try {
    ParkingOrder visitorOrder = visitorInviteService.entryByPlateNo(plateNo); // @Transactional
    ...
} catch (RuntimeException e) { ... }   // 吞掉异常，但内层已把外层事务标记 rollback-only
```
内层 `@Transactional` 默认 `REQUIRED` 加入外层事务，抛异常后 Spring 将事务标记为 rollback-only；外层捕获后继续提交 → `UnexpectedRollbackException`。

**建议**：`entryByPlateNo` 改 `@Transactional(propagation = Propagation.NOT_SUPPORTED)`，或在 `deviceEntry` 外层不做事务包装；捕获后返回明确业务语义（"未注册车辆或黑名单，请人工确认"）。

**已注册车牌链路正常**（实测 `湘A2T817` → 分配 A-005 → 生成订单 → 抬杆），说明 IoT 联动主干是通的。

### P1-2 占用率统计恒为 0

```
GET /api/stats/occupancy?startDate=2026-10-20&endDate=2026-10-28
→ {"dates":[…],"totalSpaces":[0],"occupiedSpaces":[0],"avgOccupancy":0.0}
```
`ParkingStatsServiceImpl.updateStats()` 新建行时 `setTotalSpaces(0)` / `setOccupiedSpaces(0)`，此后**只有 entry/exit 计数被更新**，从未回填真实车位数与占用数。前端统计页"平均利用率 0.0%"、占用率图表全 0。

**建议**：`updateStats` 时通过 `parkingSpaceClient` 拉取 `status/statistics` 回填；或用定时任务按小时快照。

### P1-3 未注册车牌的"设备入场"整体不可用（与 P1-1 同源）

`deviceEntry` 的"未识别 → 访客白名单兜底"分支在目标车牌不在白名单时必然抛上述异常，等于**该分支永远走不通**。需要按 P1-1 修复后重测。

### P1-4 预约时长上限只在前端

前端 `reserve` 页限制 ≤2 小时并校验不早于当前时间；后端 `reserveSpace()` **无时长上限、无"不得早于当前"校验**。
实测：直接调接口预约 24 小时 → 成功。

**建议**：把 2h 上限与时间下界下沉到 `ParkingSpaceServiceImpl`，前后端同源（建议把上限提到配置项）。

### P1-5 业主可读他人订单详情/费用/账单

| 调用 | 结果 |
| --- | --- |
| `GET /api/order/{orderNo}`（他人订单） | ✅ 返回完整订单 |
| `GET /api/order/calculate?orderNo=` 他人订单 | ✅ 返回金额 2340.00 |
| `GET /api/payment/bill?orderId=` 他人订单 | ✅ 返回账单 |

`ParkingOrderController.detail()` / `calculate()` / `PaymentRecordController.bill()` 均未校验归属。列表接口已做 role=0 强制过滤，但详情类接口漏了。

**建议**：三个接口统一加"订单归属 = 当前 X-User-Id 名下车辆"校验，或对 role=0 复用 `list` 的过滤逻辑。

### P1-6 业主可读/改他人通知

```
GET /api/notify/list?userId=1002      → 返回 userId=1 与 1001 的通知
PUT /api/notify/readAll?userId=1002   → 成功
```
**建议**：`NotificationController.list/readAll/unreadCount` 对 role=0 忽略入参 `userId`，强制取 `X-User-Id`（与 `/user/info` 同一写法即可）。

### P1-7 前端区域筛选缺 D 区

库中车位分布：`C:33 / D:20 / A:17 / B:17`（空闲：`C:24 / D:19 / B:11 / A:8`）。
前端 `parking/index.vue:279` 与 `reserve/index.vue:150` 都写死 `const areas = ['A','B','C']`。
后果：**D 区 20 个车位（19 个空闲）在筛选与地图统计中完全不可见**，业主预约时也选不到。

**建议**：区域改为从 `/parking/status/statistics` 的 key 动态生成，或在后端提供区域字典接口。

### P1-8 邀请列表把已过期记录显示为"有效"

前端 `statusMap[status]` 直接映射 `0→有效`，但后端 `status` 是**惰性更新**（只有访客尝试入场时才把过期记录置 2）。
实测：`ME79HN / 湘D****1 / 有效期至 2026-09-23 10:25` 仍显示"有效"。
PC 端汇总区算了 `isExpired`（统计为"已失效"）却仍用 status 渲染行内标签 → **同一页面自相矛盾**。

**建议**：前端统一用 `status === 0 && expireTime > now` 判定"有效"；后端可加定时任务或查询时惰性刷新。

### P1-9 缺 404 兜底路由，错误地址整页纯白

```
访问 /no-such-page
→ #app.innerHTML === "<!---->"，页面全白
→ 控制台仅一条 warning: [Vue Router warn]: No match found for location with path "/no-such-page"
```
**建议**：`routes` 增加 `{ path: '/:pathMatch(.*)*', component: NotFound }`，并在守卫里对未知路径跳 `/dashboard`。

| 编号 | 问题 | 说明 |

## 五、验证通过的部分（可用于回归基线）

### 认证与权限矩阵
- 三种角色真实登录成功，返回 `accessToken + refreshToken`（无用户信息，需二次 `/user/info` 拉取，前端已如此实现）
- 密码错误 / 验证码错误 / 缺验证码 / 验证码复用 / 用户不存在 → 均返回 `code=5101` 且**验证码一次性消费生效**
- 无 token → `401 未提供认证令牌`；伪造 token → `401 认证令牌无效`
- 连续登录触发 `429 请求过于频繁`（限流生效）
- 业主越权改他人资料 → 后端强制改写为本人 ID，他人数据未变（实测未篡改）
- 业主访问 `/api/user/list` `/api/audit/list` `/api/device/list` `/api/stats/income|occupancy|peak|export` → 全部 `403`
- 业主访问 PC `/parking` `/audit` → 路由守卫重定向 `/dashboard`，菜单按角色正确过滤
