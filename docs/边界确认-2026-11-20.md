## 2. 业务范围边界

**边界内（本系统负责）**

| 能力 | 落点 |
|---|---|
| 车位资源与出租关系 | `parking_space.owner_id` = 承租关系（**不是产权**） |
| 临停/月租/访客/新能源计费 | `billing_rule` 4 条规则，自然日封顶 |
| 入场识别 → 计费 → 出场结算 → 支付 → 开闸 | order ↔ payment ↔ device |
| 欠费催缴与黑名单 | `ArrearageScanTask` + `vehicle.status=1` |
| 月卡售卖与续期 | `monthly_card_order`（vehicle 域） |
| 访客邀请、共享车位分成、发票、对账 | order / parking / payment |
| 管理端（物业）+ 业主端 H5 | web 3000 / h5 3001 |

**边界外（明确不做，需求来了先拒绝）**

| 不做 | 原因 / 替代 |
|---|---|
| 产权车位销售、产权登记、车位管理费账单 | 属不动产登记职责；确有产权车位的小区，物业核一个低价月租表达即可 |
| 车位权属字段（`ownership_type`） | 已由需求方 2026-11-20 明确否决，**不要重新引入产权模型** |
| 单车月度累计硬封顶 | 当前 450 元是「日封顶 × 30」的量级推算，不是额度控制；要做需新增月度聚合 |
| 家人车辆共用同一承租车位的归属判定 | `space.owner_id == vehicle.owner_id` 的固有边界，按临停计费 |
| 微信真实支付 | 微信无公开沙箱，保持模拟通道 |
| 分布式追踪（Zipkin/Tempo） | 已知缺口，未接入 |
| 微服务编排进 docker-compose | 只编排基础设施，服务逐个本地启动 |

## 4. 接口边界

**三层，职责不重叠**

| 层 | 路径 | 谁能调 | 守卫 |
|---|---|---|---|
| 对外 | `/api/**` | 登录用户（JWT） | 网关 `AuthGlobalFilter` |
| 管理端 | `/api/audit/**`、`/api/device/**`、写计费规则、发票 admin 等 20+ 条 | role=1 物业 / role=2 超管 | `ADMIN_ONLY_PATTERNS`（支持 `METHOD /path`） |
| 内部 | `/api/*/internal/**` | 只允许服务间 | 网关校验 + **`InternalApiGuardFilter` 在 8081-8090 各自再校验一次** |

**白名单只有 6 条**（`AuthGlobalFilter.java:52`）：login / register / refresh / captcha / `avatar/**`（`<img>` 不带 JWT）/ `payment/callback/**`（靠验签）。
`/api/**/internal/**` 已从白名单移除，实测直连 8084 不带令牌 = 403、带令牌 = 200 ✅。

**内部端点 28 个**，与 `docs/internal-api-contracts.md` 的 28 条一一对应（编号 1–27 + 5b）。

**依赖边（无环）**：
```
order → user(audit) / notify / parking / vehicle
payment → user(audit) / order / parking / device
vehicle → user(audit) / order(billing)
device → order
stats → order / payment / parking
notify → user / order
```

> 实现方式是 `RestTemplate` + `InternalHttp` 统一注入令牌，**不是 OpenFeign**。AGENTS 第 3 节写「必须用 OpenFeign」与实际不符，属规范口径失真（不影响运行）。

## 5. 安全边界

| 项 | 现状 | 判定 |
|---|---|---|
| JWT / AES 密钥 | 环境变量 → 配置 → 内置开发默认值 | ✅ 可注入 |
| `strict-secrets=true` | JWT/AES 缺失或内部令牌为默认值 → **拒绝启动** | ✅ 覆盖 3 类（已扩容） |
| `X-Internal-Token` | 默认 `SmartParking-Internal-2026`；strict 下等于默认值即拒绝启动 | ✅ 已纳管 |
| `callback-secret` | 默认 `SmartParkingCallback2026`；strict 下等于默认值即拒绝启动 | ✅ 已纳管 |
| `payment.mock-enabled` | 默认 true；strict 下必须显式 false，否则拒绝启动 | ✅ 已纳管 |
| 敏感字段 | 手机/车牌/身份证 AES-256 + `@Sensitive` 脱敏 | ✅ |
| 密码 | BCrypt | ✅ |
| 逻辑删除 | 18 张业务表全含 `is_deleted` | ✅ |
| 越权 | 业主端身份取网关 `X-User-Id`，不接受前端传参 | ✅ |

**已收口的缺口**：`strict-secrets` 原只管 JWT/AES，现已扩为「生产模式总闸」：

- `common-core` 的 `SecuritySecretsConfig` 增加内部令牌校验（为空或等于 `Constants.DEFAULT_INTERNAL_TOKEN` → 拒绝启动）；
- payment 的 `PaymentStrictModeGuard` 校验回调密钥非默认值 + `mock-enabled=false`（两项只有 payment 配置，放公共模块会误伤其他服务）；
- 默认值统一收口到 `Constants`，三处 `@Value` 占位符对齐，顺带修掉 payment 侧漏写 `SP_INTERNAL_TOKEN` 前缀导致内部调用恒 403 的隐患；
- 单测：`SecuritySecretsConfigTest`(4) + `PaymentStrictModeGuardTest`(5) 锁住四个方向的组合。

**注意**：strict 只保证"不会带着默认值上线"，不等于"生产可上线"——真实渠道密钥、TLS、备份策略仍需人工确认。

## 6. 资金边界（本次确认的最大问题）

### 6.1 停车订单：闭环 ✅

```
H5/Web 下单 → order 生成 parking_order
  → payment 创建 payment_record → 支付宝沙箱收银台
  → 回跳带 payNo 补查 / notify 验签
  → payment.paymentSuccess() 本地事务提交
  → order.internal/confirm-payment 置已支付
  → afterCommit 异步 device.internal/gate/release 抬杆
```
金额锁定在结算时，渠道金额与应付不一致拒绝入账，退款走原路回 `refund-callback`。**这条通道是完整闭环**。

### 6.2 月卡：✅ 已收口（2026-11-20 采用方案 A）

**修复前**：
```
H5 /monthly → vehicle /vehicle/monthly/create
  → vehicle /vehicle/monthly/pay  ← 自己生成 MOCK- 流水，直接置 pay_status=1
  → 无 payment_record、无收银台、无第三方流水
```
后果：收入统计漏账（只 `SUM(payment_record)`）、发票开不出（按 `payment_record.orderId` 找流水）、
`mock-enabled=false` 时端点报「请通过收银台支付」而收银台无月卡入口。

**修复后（唯一记账口径）**：
```
H5 /monthly → vehicle /monthly/create（锁价与到期承诺）
  → payment POST /api/payment/monthly/create?monthlyOrderId=&payType=
      · 金额/归属以车辆服务的月卡订单为准（忽略前端传值）
      · 业主只能为自己的月卡付款，跨用户 403
      · payment_record 记 biz_type=2 / biz_id=月卡订单ID / order_id=NULL
  → 收银台（支付宝沙箱）或模拟支付
  → paymentSuccess 按 bizType=2 分派：
      POST /api/vehicle/internal/monthly/mark-paid（幂等，重复回调不二次续期）
      —— 不调 order 确认、不分润、不开闸（月卡无停车订单）
  → vehicle 按订单承诺的 expireAfter 续期并置 type=2
```

**关键取舍**

| 点 | 结论 |
|---|---|
| `order_id` 外键 | 改为可空。月卡不属于停车订单，`order_id=NULL` 不参与外键校验（MySQL 对 NULL 不校验），外键保留 |
| 月卡续期失败 | **抛错**让本地事务回滚（流水待支付），靠渠道 query/回调重试自愈。与开闸相反（开闸失败只记日志，因为钱已收、车在出口） |
| 自助 mock 通道 | 已删除。mock 环境改走 payment 的模拟支付端点，仍可演示且记账完整 |
| 月卡退款 | 只改本表状态并原路退回，**不回滚已生效权益**（可能已使用，属人工处理） |
| 月卡发票 | **仍不支持**。发票按 `payment_record.orderId`（停车订单）找流水，月卡 `order_id` 为 NULL |
| 收入统计 | 自动覆盖 —— `sumPaidAmount` 直接 SUM `payment_record`，月卡随之计入 |

**验证**：`PaymentBizTypeRoutingTest`(4) 锁分派方向（含 null 走停车单、未知值不当月卡）；
`MonthlyCardInternalApiContractTest`(4) 锁两端口契约；E2E 月卡用例改为「下单→建流水→核销→校验到期→重复被拒」。

### 6.3 分润与对账

- `share_income` 业主分成比例已配置化：`smart-parking.share.owner-ratio`（env `SP_SHARE_OWNER_RATIO`，默认 0.7）。合法区间 (0,1)，非法值回退默认并 WARN —— 不抛错，因为分润失败虽不阻断支付却会造成静默漏账，一条明确的 WARN 更利于运维发现。物业占比为 `1 - 该值`；拆分时业主金额四舍五入、物业取差额，保证两笔之和精确等于原额（`PaymentShareRatioTest` 锁住这两个方向）。
- **已知边界**：比例是**全局**配置，尚未做到按车位/小区差异化。若后续要做「不同小区不同分成」，需要给 `share_income` 增加小区维度并从 `parking_space` 反查，属新需求而非遗漏。
- 对账 `payment_reconciliation` 只覆盖 `payment_record`，月卡同样不在内（同 6.2）。

## 7. 部署与运行边界

| 项 | 边界 |
|---|---|
| 数据库 | 单一 `smart_parking` 库，18 张业务表 + 8 张 Flyway 历史表；保留物理外键 |
| 启动顺序 | **硬依赖**：user → parking → vehicle → order → payment；notify/device/stats 只依赖 user |

| 容器 | `docker-compose` 只编排 MySQL/Redis/Nacos/RabbitMQ/Prometheus/Grafana |
