# intent.md — 原始需求（杜绝二次解读）

> 工件来源：AI 原生 SDLC「规划阶段」产出。本文件**原汁原味**留存需求，锁定原始问题，避免 AI 过度优化导致的需求偏差。
> 由 `计划书.md` 与项目现状提炼，**未经润色改写核心诉求**。

## Requested by
- 业主 / 物业管理员 / 访客（三类终端用户）；系统设计与实现者（毕业设计 / 产品化项目）

## What they said（原始诉求原文）
- “小区停车难：进出排队、人工登记、现金收费、对账繁琐、纠纷难追溯。”
- “业主想在线看车位状态、查进出记录、在线缴费、邀请访客；物业想管车位/审车辆/出报表/管费用；访客想凭邀请码自助入场。”
- “系统要响应 < 2s、并发 500+、可用率 ≥ 99.5%、数据加密脱敏、操作可审计；微服务要能水平扩展。”
- “现有实现已超出原计划：多了 `smart-parking-ai`（车牌识别/智能客服）、多了 `community/reservation/share_income/feedback/payment_reconciliation` 等表、支持多小区。这些增量需要被正式纳入管理。”
- “用 AI 编码工具提效后，团队流程跟不上：评审/规划/部署拖后腿，AI 生成代码质量参差不齐、构建还失败了。需要一套能管住 AI 速度的流程。”

## What problem this solves
1. 住宅小区“停车难”与人工管理低效、难追溯。
2. 在已用 AI 工具加速编码的前提下，**用 AI 原生 SDLC 治理“快而错 / 快而乱 / 快而滞”**：把需求、设计、计划、测试、审查、监控全部沉淀为可追溯工件，并形成监控→故障→新需求的自动闭环。

## Why now
- 代码量已具规模（12 后端模块 + 前端），但**缺少统一规范、测试、CI 与监控闭环**，且上一次构建在 `smart-parking-user` 失败——再不治理，AI 高速开发会持续放大错判与漏判。

## Constraints already known
- 技术栈锁定：Spring Boot 3.2.4 / Cloud 2023.0.1 / Alibaba 2023.0.1.0（强版本约束）。
- 数据库：统一单库 `smart_parking`（已含 16 张表，含计划外增量表）。
- 不引入 Seata AT；分布式事务走本地事务 + RabbitMQ 最终一致性。
- 敏感字段必须 AES-256 落库 + API 脱敏；密码 BCrypt。
- 交付物需支持答辩/产品化：含可运行系统、文档、ER 图。

## Explicitly out of scope（本次迭代不做）
- 不重写已稳定的业务逻辑（订单/支付/计费公式经测试验证）。
- 不引入新中间件（如 Elasticsearch 业务存储、Seata）。
- 不替换现有前端框架（Vue3 保留）。
- 不做多租户SaaS化改造（多小区用 `community_id` 列已满足当前需求）。
