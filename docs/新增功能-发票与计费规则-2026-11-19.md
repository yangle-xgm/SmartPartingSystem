## 二、日封顶改为自然日

### 原实现的问题

旧实现按「入场时刻起 24 小时滚动块」切分：周一 08:00 入场停到周二 08:30，被切成
[08:00–次日08:00] 与 [08:30 那半小时] 两块。业主看到的账单日封顶额度与「今天」无关，
跨日订单还会在 0 点后继续吃前一天剩下的额度（或反过来多收一个计费单位）。

### 现实现

按 `00:00` 切自然日，逐日累加、逐日取「当日封顶」的较小值：

- 免费时长只在第一段扣一次；
- **单位余数跨段结转**（`carryMinutes`），避免每个 0 点边界各多收一个计费单位；
- 最后一段不足一个单位仍按一个单位收（与「不足一个计费单位按一个单位」口径一致）；
- **费率按段所在自然日判周末**：周六入场、周一出场不再整单按周末价收。

### 回归用例（`BillingAndErrorCodeTest`，直接反射调用生产方法）

| 场景 | 期望 |
| --- | --- |
| 25 分钟 / 免费 30 | 0.00 |
| 35 分钟 / 免费 30 / 2.5 元每 30 分钟 | 2.50 |
| 24h30m / 免费 30 / 封顶 200 | **60.00**（旧滚动块实现会收 62.50，旧旧实现收满 200） |
| 同一自然日内 14h / 封顶 30 | 30.00 |
| 20h 跨两天 / 封顶 30 | 40.00（30 + 10，逐日各算一次额度） |
| 48h / 封顶 30 | 80.00（30 + 30 + 20） |
| 周六 08:00 起 48h / 周末 5.0 工作日 2.5 | 220.00（80 + 120 + 20） |

## 三、计费规则管理

### 接口（order 模块）

| 方法 | 路径 | 权限 |
| --- | --- | --- |
| GET | `/api/order/billing-rules` | 公开只读（原有） |
| POST | `/api/order/billing-rules` | 管理员 1/2 |
| PUT | `/api/order/billing-rules/{id}` | 管理员 1/2 |
| DELETE | `/api/order/billing-rules/{id}` | 管理员 1/2 |

- 网关 `ADMIN_ONLY_PATTERNS` 按方法精确拦截，GET 保持公开（H5 结算页要用）。
- 服务侧 `requireAdmin` 双保险 + 每次变更写审计日志（谁把单价从 5 元改成 2 元可追）。
- 跨字段校验：日封顶不得低于一个计费单位价格；周末封顶不得低于周末单位价；
  月租车规则必填月租价；月租价不得低于日封顶。
- 删除保护：仍有进行中订单（`status=0`）引用该规则时**拒绝删除**，否则这些车出场算不出金额。

### 页面

管理端新增 `/billing`（停车运营 → 计费规则）：列表 + 新增/编辑抽屉 + 删除确认，
顶部四个统计卡（规则总数 / 已启用 / 临时车 / 月租车）。

## 四、电子发票

### 表（payment 模块，`V5__invoice.sql`）

`invoice`：`order_id`（唯一，一单一票）、`payment_id`、`user_id`、`title_type`、
`title`、`tax_no`、`email`、`amount`、`status`、`remark`、`apply_time`、`issue_time`。
外键指向 `parking_order` / `sys_user`，并建 `idx_user_time`、`idx_status`。

### 状态机

`0 待开票 → 1 已开票 → 2 已红冲`。开票与红冲都用条件更新（`WHERE status=<期望值>`）
防并发重复开票；红冲后同一订单不再重开（唯一键限制），需人工处理。

### 接口

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| POST | `/api/payment/invoice/apply` | 业主 | 申请开票 |
| GET | `/api/payment/invoice/my` | 业主 | 我的发票 |
| GET | `/api/payment/invoice/admin/list` | 管理员 | 列表（状态/关键字筛选） |
| POST | `/api/payment/invoice/admin/{id}/issue` | 管理员 | 开具 |
| POST | `/api/payment/invoice/admin/{id}/red-flush` | 管理员 | 红冲（带原因） |

### 关键边界

- **金额取实际收款流水**（`payment_record`），不取订单应收金额：零元放行单、减免单不产生发票，
  订单金额后续可能被改，只有流水是真金白银；
- 校验订单 `payStatus=1`，且流水 `userId` 必须等于申请人（只能给本人付的钱开票）；
- 实付金额为 0 直接拒绝；
- 一单一票：先友好提示，并发时由 `uk_order_id` 兜底。

### 页面

- **H5**：支付记录页每笔成功流水右下方出现「申请发票」，弹层填抬头类型/抬头/税号/邮箱；
  已申请过的显示「已申请，待开票 / 发票已开具 / 发票已红冲」且按钮禁用。
- **管理端**：新增 `/invoice`（缴费管理旁），筛选 + 开具 + 红冲（红冲强制填原因，写入备注并记审计）。

## 五、已知风险与未做项

1. **H5 月卡「模拟支付」是真实的免费通道** —— `POST /api/vehicle/monthly/pay` 直接把订单置成功并延期，
   业主点一下就白拿月卡。当前只在业务语义上标注「模拟支付」，**没有环境开关**。
   毕业设计演示可接受，若作为生产基础必须：接入真实支付 or 加 `smart-parking.mock-pay-enabled`
   开关（默认 false，生产关闭）。
2. **发票不对接税务平台** —— 只做单据流转与状态机，正式开票需在税控系统完成后再回填发票号。
   这是需求方确认的范围边界。
3. **计费规则无版本快照** —— 改规则只影响之后创建的订单；已在场订单仍按入场时匹配的规则结算，
   因为订单存的是 `billing_rule_id` 而非规则快照。若规则被物理删除会走「规则缺失」拒付 + 人工放行。
4. **真实支付渠道 / 设备厂商渠道** —— 毕业设计不接入，详见 §1。
