## 六、本轮额外发现并修复的 3 个阻断级问题

> 这 3 个问题不在原报告里，但都属"部署即失败"或"上线即出事"级别。

### 6.1 Flyway `baseline-version: "2"` 导致新库第 2 个模块起全部跳过建表（致命）

8 个模块共用一个 `smart_parking` schema。任一模块先建表后，schema 对后续模块就是"非空"，而 `baseline-on-migrate: true` + `baseline-version: "2"` 会让后续模块**把自己的 V1/V2 当基线跳过**——表永远建不出来。实测 payment 启动即 `Table 'smart_parking.payment_record' doesn't exist`。

修复：`baseline-version` 全部下调为 `"0"`；8 个 `V1__init.sql` 的建表统一改 `CREATE TABLE IF NOT EXISTS`；user/parking 两处 `ALTER TABLE ... ADD COLUMN community_id` 改为 `information_schema` 幂等判断；V2 种子本就是 `INSERT IGNORE`。改完在**空库**上串行启动 8 个模块，V1→V4 全部 `Successfully applied`。

### 6.2 支付回调被网关拦成 401，验签代码永远走不到

`/api/payment/callback/**` 不在网关 `WHITE_LIST`，渠道回调（不带 JWT）一律 401，P0-2 补的验签逻辑实际是死代码。已加入白名单（安全性由服务端验签保证）。

同时发现并修复：`PaymentTimeoutTask` 把流水置 `CLOSED(3)` 后，渠道真的扣款成功时回调会被 `pay_status in (0,4)` 挡掉 → **用户付了钱、系统记关闭**的掉单。改为 `in (0,3,4)`，遵循"渠道事实优先于本地超时判断"，但仍只挡 `PAID(1)`/`REFUNDED(2)` 防回跳。

### 6.3 队列 `acknowledge-mode: manual` 但消费者从不 ack

order 模块配了手动 ack，新加的消费者没调用 `basicAck` → 消息永远停在 unacknowledged（实测 `messages_ready=0 / unacked=1`，看起来"没人消费"，重启后又被重投）。已按本项目既有写法（`Message + Channel`）显式 `basicAck`/`basicNack`。

同时修掉一个**我自己引入的**死循环：金额不一致时无脑 `throw` 会让毒消息每秒重投一次、刷满日志并堵住队列。现按异常性质分流——`BizException` ack 掉 + ERROR 留痕（`[掉单待人工]`），`DataAccessException` 才 nack 重投。

## 七、部署/运维变更须知

1. **Flyway 现在是唯一权威建库路径**：空库启动即自动建表灌种子。模块启动顺序有硬依赖 `user → parking → vehicle → order → payment`，`notify/device/stats` 只依赖 user。
2. **E2E/演示数据需额外两步**：服务起来后执行 `mapper/seed_more.sql`、`mapper/seed_community23.sql`（小区 2/3、zhaoliu 等账号），E2E 用例依赖这些数据。
3. **生产必须覆盖的密钥**：`SMART_PARKING_JWT_SECRET`、`SMART_PARKING_AES_KEY`、`SP_INTERNAL_TOKEN`、`smart-parking.payment.callback-secret`、`smart-parking.payment.mock-enabled=false`、`SP_CORS_ORIGINS`。设 `smart-parking.strict-secrets=true` 可让缺密钥时拒绝启动。
4. **本地起全部 10 个服务会打爆内存**（28G 机器剩不到 600M，导致 `mvn test` 的 surefire fork 起不来）。建议分批启动并加 `-Xmx`，或跑测试前先停服务。
